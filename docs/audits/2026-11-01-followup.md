# Follow-up review — 1 November 2026

Starting point: `370922a767bc92ee5b1a8962cf289d175f3ed5c3` (v1.9.12).

Reviewed settings/provisioning, notification delivery, saved statistics,
firmware trials, V1/V2 connection supervision and asynchronous dashboard
requests. The reproducible faults found in this pass are corrected below.

| Fault | Correction | Regression coverage |
|---|---|---|
| A pool could authorize/open a channel without delivering work. Authorization disabled the handshake timeout and reset the failover counter, leaving mining idle and preventing the backup from being selected. | V1 and V2 require initial usable work within the 30-second setup deadline. A session without work counts as a failed attempt, so three such main-pool attempts select the configured backup. Existing work does not need to refresh every 30 seconds. | Real V1 session and reconnect loop, V1/V2 backup selection, timer wrap, valid long-running work, and an independent encrypted V2 peer opening a channel without sending a job. |
| A pending dashboard poll could deliver an old boot's snapshot after a live event from a new boot. The different boot ID was interpreted as another restart, restoring obsolete readings and resetting history again. | An accepted live snapshot supersedes any poll already in flight, including its success response. | Browser regression completing an old poll after a new boot's live snapshot; the new boot, uptime and history session remain current. |
| Failure of that older poll could mark the dashboard offline even after newer live data had arrived. | Errors belonging to a superseded poll are ignored too. | Browser regression returning HTTP 503 after a newer accepted live snapshot; the dashboard stays online. |
| A reboot during measurement preparation could go undetected if the delayed diagnostics still described the original boot and the new boot had higher counters. | Preparation retains the dashboard session and rejects a changed session or firmware before starting the measurement. | Browser regression delivering old diagnostics after a new boot with higher uptime and hash totals; no measurement starts. |

The new V1 timeout and all three dashboard regressions failed before their
corrections. Tests use local deterministic peers and mocked browser APIs;
no hardware or public mining pool is contacted.

## Notification delivery and firmware confirmation

A further fault-injection pass starts at
`88b7c4ca609581359b91fdc471a05d88cce76e41`.

| Fault | Correction | Regression coverage |
|---|---|---|
| An unsuccessful bootloader confirmation cleared the firmware's pending-trial flag. The dashboard stopped reporting a pending trial and the periodic poll never retried confirmation. | Restore the pending flag on failure. Retain the trial metadata until confirmation actually succeeds. | Inject a confirmation failure through the production function and poll, then allow success: the flag stays pending, metadata remains intact, polling retries, and success confirms once. |
| A full notification queue discarded a test but the endpoint still acknowledged it as queued. | Queueing reports failure. The HTTP endpoint returns 503 for a busy queue and retains 409 for notifications not configured since startup. | Production queue and HTTP handlers with six queued alerts, unauthenticated requests, disabled delivery and retry after draining the queue. |
| The settings page accepted the first changed delivery counter as its test result, including an unrelated alert. Later alerts could also overwrite the completed test before the page read it. | Each accepted test gets an ID. The page requests that test's result; the last eight test results are retained independently of ordinary alert status. | Distinct queued tests, intervening alerts, destination-specific retries, bounded retention, ID wrap, HTTP ID validation and a browser receiving an unrelated result before its actual result. |
| Editing settings re-enabled the test button while a test was pending; discarding edits replaced the result element, so the eventual result was written to a detached node. | Pending state locks the test button across settings changes. The message survives form rendering and completion updates the current element. | Browser changes a select and discards edits during a gated POST: exactly one request is made, the button stays locked and the final result appears in the replacement form. |

`POST /api/notify-test` now returns JSON `{"id":N}` after queueing a test.
`GET /api/notify-test?id=N` returns its retained result; an `id` of zero in the
response means no matching completed result is currently retained. Omitting the query selects
the latest completed test. The dashboard integration status continues to
describe the latest ordinary or test delivery.

The two native fault injections and all three new browser regressions fail
against the corresponding previous code. The corrected browser suite has
88 passing cases. Notification tests replace both network senders locally;
no external notification is sent. Hashing kernels, clock profiles and thermal
thresholds are unchanged by this pass.
